# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**dependably** is a self-hosted private artifact repository for npm, PyPI, NuGet, Maven, RPM, OCI images, Go modules, and Cargo crates. Core design priorities: supply chain awareness (first-fetch tracking, checksum verification, SBOM generation) and multitenancy (org isolation, scoped tokens, BOLA protection).

Tech stack: **ASP.NET Core 10 / C#**, **Dapper** (parameterized SQL only — no string interpolation), **SQLite** (`IMetadataStore` / `SqliteMetadataStore`), **Serilog** structured JSON logging, **JWT** sessions, **BCrypt** passwords, **NuGet.Versioning** for NuGet version normalization. **ASP.NET Core Identity Core** (`AddIdentityCore` only, no SignInManager/cookie scheme) over custom Dapper `IUserStore` implementations supplies the MFA and credential primitives (TOTP, recovery codes, BCrypt hashing, security_stamp); the first-factor login, lockout, JWT session, and per-request session-invalidation layers are bespoke for security reasons documented in `ADR-auth-identity-hybrid`.


## Project structure

The backend is four assemblies (the assembly split lets a slim edge image ship without the
management-plane dependency closure):

```
src/Dependably/             — thin composition root (Program.cs only); refs Core + Management;
                              assembly name "Dependably", entrypoint ./Dependably → image dependably/community
src/Dependably.Core/        — protocol + storage + infrastructure classlib (the shared closure)
src/Dependably.Management/  — admin/auth/SAML/SPA/docs classlib; management tables dormant on edge
src/Dependably.Edge/        — edge composition root (Program.cs); refs Core only, never Management;
                              entrypoint ./Dependably.Edge → image dependably/edge
```

Most of the protocol, storage, and infrastructure tree lives in `Dependably.Core`; the
admin/auth surface lives in `Dependably.Management`. Tests are in `tests/Dependably.Tests/`
(`Unit/` no-I/O, `Integration/` via `DependablyFactory`, `Fixtures/packages/` real artefacts).

## Key architectural rules

- **BlobKeys is the only place blob keys are constructed.** Callers never build key strings inline — enforced by the `BlobKeyConstructionComplianceTests` test (inline literal/interpolated keys passed to `IBlobStore` members fail; opt out a deliberate non-namespaced key with `// blobkey-ok: <reason>`).
- **All Dapper queries must use parameterized form.** No string interpolation inside SQL — enforced by the `NoInterpolatedSqlComplianceTests` test (the `SecurityCodeScan` analyzer also flags it as an advisory warning, but the test is the gate). A compile-time-constant interpolated fragment (e.g. a whitelisted `ORDER BY`) opts out with a `// rawsql: <reason>` comment in the 5 lines above the SQL literal.
- **SQL touching tenant-scoped tables must filter on `org_id`/`tenant_id`** — enforced by the `OrgIdFilteringComplianceTests` test. Legitimately cross-tenant queries (one-shot migrations, system-admin views, queries keyed by an FK-bound id that's already org-scoped) opt out with a `// xtenant: <reason>` comment in the 5 lines above the SQL literal. The table set is **derived from `Schema.sql`** (every `CREATE TABLE` declaring `org_id`/`tenant_id`), so a new tenant-scoped table is covered the moment it lands in the schema; only the read-model views and the version-scoped child tables are named by hand, and each is asserted to exist. All three C# string forms are scanned — raw, verbatim, and plain — with concatenated literals coalesced, and the filter check requires the tenant column in a **filtering position** (`WHERE`/`ON`/`HAVING`/`USING`, or an `INSERT` column list), rejecting projections, aliases, and inverted (`!=`/`<>`/`NOT IN`) predicates. **Its real remaining weakness is data flow, not syntax:** the gate cannot tell whether `@orgId` was bound from the authenticated principal or straight off a route parameter — the latter is textbook BOLA and passes green — and column-to-column predicates (`WHERE p.org_id = c.org_id`) pass because they are correct inside a correlated subquery whose outer query is bound. Only a reviewer closes that gap.
- **Every management-plane action carries an explicit authorization decision** — enforced by the `AuthorizationDecisionComplianceTests` test. There is no `FallbackPolicy` and deliberately cannot be one (`RouteScopeFilter` passes unauthenticated requests through by design, and the protocol plane authenticates outside ASP.NET authz), so this gate is the backstop. An action satisfies it with `[Authorize]`/`[RequireCapability]`, or with `[AllowAnonymous]` **plus** an `// authz-ok: <reason>` marker in the 5 lines above, or — for the hand-rolled `SiemController`/`AuthController.Logout` shape — with the same marker and no attribute. A bare `[AllowAnonymous]` fails: the marker is what makes the decision reviewable. Protocol controllers are gated at controller granularity (each must resolve a token somewhere in its own source, partials included) because their per-ecosystem token schemes cannot flow through attribute policies.
- **Comments describe the current architecture, not its development history.** No issue/tracker numbers (`#123`), milestone tags (`M2.1`), or ephemeral branch/PR pointers (`this PR`, `see plan §2`, `pre-#91`, `used to…`) in code or config comments — that provenance belongs in git history and the issue tracker, not the source. Write present-tense descriptions of how the code behaves now. The unambiguous patterns (`#NNN`, `M<x>.<y>`, `this PR/MR`, `see plan`, `pre-#`) are enforced over `src/**/*.cs` comments by the `CommentProvenanceComplianceTests` test; the prose-history form (`used to…`) is a guideline a regex can't safely distinguish from present-tense purpose, so it stays reviewer-enforced. (Functional markers such as the `// xtenant:` / `// rawsql:` / `// blobkey-ok:` opt-outs and `// deepcode ignore` suppressions are not provenance and are fine.)
- **Project files (`*.csproj`, `*.props`) carry no XML comments.** Rationale for package pins and build config belongs in git history, the issue tracker, and project memory — not in inline `<!-- … -->` essays that drift from the truth and read as AI slop. Enforced by the `ProjectFileCommentComplianceTests` test (any `<!-- … -->` in a `.csproj`/`.props` outside `bin`/`obj`/`node_modules`/`.claude` fails). A deliberate, rare comment opts out with an inline `<!-- csproj-comment-ok: <reason> -->` marker.
- **Wall-clock reads go through the injected `TimeProvider`** (`TimeProvider.System` registered as a DI singleton; static helpers take the timestamp as a parameter, like `MavenMetadataBuilder.Build`). No `DateTime.Now/UtcNow/Today` or `DateTimeOffset.Now/UtcNow` in src or tests — enforced by the `TimeDeterminismComplianceTests` test. Tests freeze time with `FakeTimeProvider` (`TestTime.Frozen()` / `ControllerScenario.Clock` / `DependablyFactory.FrozenClock`) and assert exact instants instead of tolerances; seed offsets must stay far from window boundaries (no `.AddDays(-365)` against 1-year cutoffs — leap years shift it). A deliberate wall-clock read (e.g., a test polling deadline awaiting real async completion) opts out with `// now-ok: <reason>` in the 5 lines above.
- **Waiting on and measuring with the clock go through `TimeProvider` too** — the same gate flags raw `Task.Delay`, `Thread.Sleep`, `new Timer(…)`/`new PeriodicTimer(period)`, and every `Stopwatch` form across `src/**`. These fail *silently* where a wrong `DateTime` fails loudly: a test advancing a fake clock past a raw timer's deadline observes nothing happening, so the suite stays green over semantics that do not work (a lock whose TTL never expires, a retry loop whose deadline never arrives). The TimeProvider-aware overloads — `Task.Delay(delay, timeProvider, ct)`, `new PeriodicTimer(period, timeProvider)`, `TimeProvider.CreateTimer`, `GetTimestamp`/`GetElapsedTime` — are recognised and pass. The established exceptions carry `// now-ok:` and fall into three shapes: a duration measured only to be logged or recorded as a metric (nothing branches on it), a poll loop awaiting genuine async completion on another thread, and a wait whose whole purpose is real elapsed time (`ShutdownOrchestrator`'s `Thread.Sleep` blocking `ApplicationStopping` while the load balancer drains; HTTP retry back-off against a live upstream).
- **`IBlobStore` never makes naming decisions** — keys always come from `BlobKeys`.
- **Every routed protocol action carries an explicit rate-limit policy** — enforced by the `RateLimitPolicyComplianceTests` test. The GlobalLimiter is default-deny (a protocol path with no endpoint policy gets a per-IP default limit via `RateLimitPartitions.ClassifyGlobalScope`, not `NoLimiter`), but the gate still requires each Protocol-classified controller action to declare an explicit `[EnableRateLimiting("…")]` sized for its cost — the default is a backstop, not a licence to leave a hot route (packument re-parse, catalogue scan, upstream-fetch amplification) unclassified. Opt out a deliberate reliance on the default (or a bare `[DisableRateLimiting]`) with an `// ratelimit-ok: <reason>` marker in the 5 lines above. Per-IP partition keys collapse IPv6 to its `/64` (`RATE_LIMIT_IPV6_PREFIX`) so a routed `/64` is one budget; audit `source_ip` keeps the full address (`GetRateLimitPartitionIp` vs `GetNormalizedRemoteIp`).
- **A `BlockGateRequest` is built by a factory on the record, never field-by-field at a call site** — enforced by the `BlockGateRequestConstructionComplianceTests` test. The gate threads a dozen policy modes and as many facts, and a field left off a call site does not fail to compile: it defaults to null, which every arm reads as "policy off". That has already produced two silent holes (`VerifyProvenanceMode` inert on every serve path for every ecosystem; the proxy first-fetch path reading a tenant-blind projection and so ignoring `manual_block_state`/`revoked_at`). The two proxy factories — `ForProxyCacheFacts` (cache hit) and `ForProxyFirstFetch` (post-record first fetch) — both read `CacheArtifactServeFacts`, which is what makes first-fetch and cache-hit enforcement symmetric by construction rather than by convention. A deliberate exception opts out with `// gate-request-ok: <reason>`. Which ecosystems route through `ProxyFetchService` (and so get source pinning) is pinned by `ProxyServePostureComplianceTests`; RPM deliberately does not, because its distro/release-specific repositories make "one upstream host per name" false, and it runs the same record → scan → re-read facts → gate sequence in its own handler instead.
- **Every audit write names its origin and, when it names an actor, that actor's kind** — enforced by the `AuditAttributionComplianceTests` test over `AuditRepository.LogAsync`/`LogActivityAsync` (`LogSystemAsync` is out of scope — it has no `actorKind` parameter). `sourceIp` is required on every covered call; `actorKind` is required only when the call also supplies a real `actorId` — a truly actor-less row (an anonymous login failure, a lockout) correctly carries a NULL kind rather than a fabricated one. `source_ip` uses the full address (`HttpContext.GetNormalizedRemoteIp()`), never the rate-limit-partition form. A genuinely actor-less/IP-less background path (a scheduled sweep, a single-flight upstream fetch shared by several concurrent callers) opts out with `// audit-attribution-ok: <reason>` in the 5 lines above the call; a bare marker with no reason is not honoured. The gate proves an argument was supplied, not that its value is correct — see the test's own doc comment for the full list of blind spots. Companion gate `AuditOrgIdComplianceTests` covers the separate `orgId` completeness rule on `LogAsync` (`// audit-orgid-ok:`).
- **Architectural invariants are enforced by `Category=Compliance` static-scan tests, not just docs.** The family (`OrgIdFilteringComplianceTests`, `AuthorizationDecisionComplianceTests`, `RateLimitPolicyComplianceTests`, `NoInterpolatedSqlComplianceTests`, `BlobKeyConstructionComplianceTests`, `BlockGateRequestConstructionComplianceTests`, `ProxyServePostureComplianceTests`, `CommentProvenanceComplianceTests`, `ProjectFileCommentComplianceTests`, `NoDebugOutputComplianceTests`, `NoFocusedOrSkippedTestComplianceTests`, `AuditAttributionComplianceTests`, `AuditOrgIdComplianceTests`, plus the `Schema*ComplianceTests`) reads source, regexes for a banned pattern, and fails with the full list — so violations surface locally and on every MR. **Every src-scanning gate resolves its roots through `SourceRoots`** (repo root anchored on `Dependably.sln`; roots discovered by globbing `src/Dependably*` directories that hold a `.csproj`) rather than naming a project directory. A gate that hard-codes `src/Dependably` reads as comprehensive while scanning the thin composition root — it goes green-but-blind, which is strictly worse than going red. `SourceRoots` is also what makes a new `src/` project covered the moment it lands. Metric attribute names are a **closed allowlist** (`CardinalityBudgetTests.AllowedAttributeNames`) for the same fail-closed reason: a denylist of obvious identifier names says nothing about an innocuously named attribute carrying a caller-controlled value. Production code uses Serilog (no `Console`/`Debug` output outside the allowlisted first-boot banner) and ships no `NotImplementedException` stubs; no committed test is focused (`.only`/`fit`/`fdescribe`) or skipped (`.skip`/`[Fact(Skip=…)]`, opt out a deliberate skip with `// skip-ok: <reason>`). Prefer adding a compliance test over a CI grep when codifying a new rule.
- **Schema changes must stay readable by the *previous release*** — enforced by the `SchemaBackwardCompatibilityComplianceTests` test. Blue-green runs both versions against one database during the cutover window, so a dropped table or column, a narrowed `CHECK (col IN …)` value set or any other added or changed `CHECK` clause on a surviving column, or a column that stops being omittable from an `INSERT` (loses `NOT NULL` + `DEFAULT` cover) breaks the old slot mid-deploy. The gate resolves the previous release tag, extracts `Schema.sql` / `Schema.pg.sql` at that tag, and diffs each provider file against its own baseline. Opt out the deliberate contract step of an expand/migrate/contract sequence with a `backcompat-ok: <table>[.<column>] — <reason>` marker — written `-- backcompat-ok:` in a schema file, `// backcompat-ok:` in a `SchemaInitializer*.cs`; a marker naming an object but giving no reason is rejected as malformed and not honoured. The comparison is **declarative only** — it never reads `SchemaInitializer`'s DDL (it does read those files for waiver markers), so migration-applied changes (`RunOnceAsync` drops, `ADD CONSTRAINT … CHECK` narrowings, table rebuilds) and the views recreated on every boot are outside its reach. `SCHEMA_BACKCOMPAT_REQUIRE_BASELINE=true` (set on the `schema-integrity` job) makes an *unreadable* baseline a failure rather than a silent pass — a network blip, an unreachable origin, or a stripped remote cannot turn the gate into a no-op; a repository that genuinely has no release tag yet still passes.
- **`IMetadataStore` returns raw connections.** Callers use Dapper extension methods and are responsible for `await using`.
- **PURLs are the canonical package identity.** `PurlNormalizer` is the single source of truth — used by push handlers, proxy handlers, simple index generator, and npm metadata rewriter.
- Registry routes: `/simple/`, `/npm/`, `/nuget/v3/index.json`, `/maven/`, `/rpm/`, `/go/`, `/cargo/`. Tenancy is host-resolved: `DEPLOYMENT_MODE=single` (default) serves the one org from the bare host; `DEPLOYMENT_MODE=multi` routes each org by subdomain (`my-org.apex/simple/` etc.). OCI has no org prefix — the Distribution Spec mandates `/v2/`. Go is proxy-only (no hosted push path).
- **Token auth**: npm uses `Authorization: Bearer <token>`; PyPI and NuGet use `Authorization: Basic base64(user:<token>)`. Resolution in `TokenAuthExtensions.ResolveTokenAsync`. Token stored as SHA-256 hash in DB.
- **NuGet push** uses `X-NuGet-ApiKey` header, not Authorization.
- **Proxy cache miss** path: check `BlobKeys.Proxy(sha256)` in blob store → if absent, fetch from upstream, verify checksum, store, serve. Upstreams are per-org, DB-backed (`upstream_registry` table), and managed from Settings → Proxy; the `PyPI:Upstream`/`Npm:Upstream`/`NuGet:Upstream` settings only seed the initial row for newly created orgs.
- **Upload size limits**: checked in order — org ecosystem limit → org global limit → instance ecosystem limit. Returned as 413 before any blob is written.
- **OpenAPI is split into two named documents.** Management endpoints (`/api/v1/…`) are documented at `/api/v1/docs/` (spec: `/openapi/management.json`); protocol surfaces (`/v2/`, `/simple/`, `/npm/`, `/nuget/v3/`, …) are documented at `/docs/` (spec: `/openapi/protocol.json`). The split is route-prefix-driven (via `OpenApiOptions.ShouldInclude` against `ApiDescription.RelativePath`), not attribute-driven — new controllers land in the right document automatically based on where they route.
- **Protocol surfaces follow upstream ecosystem specifications, not Dependably API versioning.** OCI is at `/v2/` because the Distribution Spec mandates it; PyPI is at `/simple/` because PEP 503 mandates it; npm and NuGet are at the paths their clients hardcode. Do not add internal version segments to these routes.
- **AI code review runs in CI as an advisory `ai-review` stage.** Four MR-only jobs (`ai-review-security`, `-code`, `-architecture`, `-docs`) send the MR diff to a local Ollama model and post per-lens findings as merge-request comments (plus a job-log section and a Markdown artifact). Logic lives in `ci/ai-review.sh`, per-lens prompts in `ci/prompts/`; jobs are `allow_failure: true` and never gate a release. Configuration and the `AI_REVIEW_GITLAB_TOKEN` secret are documented in `CONTRIBUTING.md` → "AI code review (CI)". Non-gating in CI does not mean non-blocking for a merge — see "Definition of done". A "no material findings" claim is never trusted on marker-absence or an unverified sentinel match alone: `classify_response` requires a byte-exact match against the sentinel the persona file declares, and even then `confirm_clean` runs an independently-prompted second pass before the result posts as clean — a diff can echo the disclosed sentinel back at the model, so exact-match alone is well-formed, not verified. Anything that is neither a recognised finding set nor a confirmed clean claim renders as `(unverifiable response)`, the same no-signal treatment as `(bad response)`. The gating `ai-review-script-test` job (`ci/ai-review-test.sh`, `test` stage, `.release-required`) regression-pins this state machine — distinct from the four advisory lens jobs it tests, which stay `allow_failure: true`.
- **A security gate never degrades to "allow" because its input signal is missing.** Three specific postures encode this: (1) an unreachable advisory source is *deferred*, not recorded — `VulnerabilityScanService` branches on `IOsvSource.TryQuery*Async(...).Reached` and leaves `vuln_checked_at` NULL so the row stays in the unscanned bucket (a stamped `vuln_checked_at` is what *enables* the malicious/KEV/EPSS/CVSS arms, so a false stamp silently disables four gates); (2) under `license_enforcement_mode=block`, zero recorded SPDX entries is an unknown licence and **blocks** for the ecosystems whose manifests declare one (`BlockGateService.DeclaredLicenseEcosystems` — npm/pypi/nuget/maven/cargo/rpm), while go/apk/oci keep the empty-set pass-through because they routinely record nothing; (3) `verify_*_signatures=block` with an **empty trust-anchor set** denies every artifact of that ecosystem rather than becoming a no-op (`BlockGateService.IsProvenanceEnforcementUnbackedAsync`, synthesizing the never-persisted `ProvenanceStatuses.Unverifiable` marker) — same posture as `Rpm:VerifyRepomdSignature` with no anchor. Correspondingly, **every field on `PUT /api/v1/proxy-settings` is leave-unchanged-on-absent** — one posture for the whole endpoint, not a per-column floor: the six `verify_*` fields plus `proxy_passthrough_enabled`, `max_osv_score_tolerance`, `block_deprecated`, `block_revoked`, `block_malicious`, `block_kev`, and `block_install_scripts` use `COALESCE(@x, x)`, not default-to-off/default-to-block. `min_release_age_hours` and `max_epss_tolerance` need a third state instead of plain COALESCE: for those two, "off" *is* SQL NULL, so a plain nullable field can't distinguish an omitted PUT field from a deliberate clear-to-off — they're carried as `Optional<T>` (`Dependably.Api.Optional<T>`, `IsPresent` + `Value`, bound via `OptionalJsonConverterFactory`) so absent/explicit-null/explicit-value stay distinguishable end to end, and the repository picks the branch with a parameterized `CASE WHEN @xSet = 1 THEN @x ELSE column END` rather than `COALESCE`. `OptionalSchemaTransformer` rewrites the two fields' generated OpenAPI schema back to a plain nullable integer/number — `Optional<T>`'s converter factory defeats the exporter's normal reflection, so without the transformer they'd render as an opaque/empty schema instead of matching every other optional field in the document. The one narrow exception is `block_malicious`'s *first-ever write for an org* (no stored row yet): the `INSERT` arm's `COALESCE(@blockMalicious, 'block')` still lands the secure default there, same as every other field's INSERT arm lands its own column default — leave-unchanged only ever preserves a row that already exists.
- **SMTP is an instance-level transport; tenants configure how Dependably *uses* it, not how mail is transported.** One relay per deployment (`instance_settings.smtp_*` via `InstanceSmtpConfig`), owned by the operator, carrying every outgoing message: invites, password resets, password-changed and MFA notices, email-change verification, and alert email. An org owns only `alert_settings.email_enabled` and `email_recipients` — a delivery channel, not an email configuration, so it is edited on Settings → Integrations alongside Slack and webhooks, not on Settings → Alerts (which keeps only what *raises* an alert). Each editing surface owns one endpoint and writes only its own columns — `PUT /alert-settings` the gates, `/alert-settings/email` the email channel, `/alert-settings/slack` the Slack channel — because a combined PUT lets a tab that no longer renders a field bind it to `false` and silently disable another tab's channel. There is no per-org SMTP config and no inheritance flag — `email_inherit_instance` and the `email_smtp_*` columns are retired and unread. They stay **declared** because releases still in the field name all seven in their `alert_settings` SELECTs and blue-green runs one of those against the same database for the length of a cutover, so removing them breaks that slot's entire alert-settings read — the Alerts page and the delivery gate, not merely the transport. Their stored values are scrubbed instead: a one-shot migration forces `email_inherit_instance` to `1` and NULLs the six transport/credential columns, which is the shape an older slot reads as "carry this org's mail over the instance transport", so no credential remains stored and no writer remains. The drop waits until the oldest release Dependably supports upgrading from no longer reads them, deliberately not pinned to a specific next release — an operator who skips intermediate versions is exactly the case a one-release deferral fails to protect. A second rule follows from the first: **delivery failure never mutates tenant configuration.** `RecordEmailFailureAsync` records health (`email_last_status`, `email_consecutive_failures`, `email_failing_since`, `email_last_error`) and deliberately leaves `email_enabled` alone, because the failing component is the operator's shared relay — auto-disabling would turn one infrastructure outage into dozens of independent tenant configuration failures, each needing a manual re-enable. Configuration is intent, health is reality, and they stay independent; auto-*re*-enable is rejected for the same reason auto-disable is. `RecordSlackFailureAsync` still auto-disables, and that asymmetry is deliberate: a Slack webhook URL is tenant-owned and tenant-fixable.
- **Alert email is durably persisted; credential-bearing mail deliberately is not.** Alert mail is written to `email_outbox` before any delivery attempt (`AlertEmailQueue.NotifyAsync`) and delivered by `EmailOutboxDeliveryService`, so the guarantee is exact and narrow: *alert email is durably persisted until it is delivered, or until an explicit terminal retry/retention policy expires it* — never "every message is eventually sent". `pending`/`sending` are the only non-terminal states; `delivered`, `dead_letter` (the message or the configuration is wrong) and `expired` (out of attempts, retry time, or retention) are terminal, and the delivery path never leaves them — only `RetentionService` deletes them, past `EMAIL_OUTBOX_TERMINAL_RETENTION_DAYS`. Classification is `EmailOutboxFailureClassifier`: SMTP 4xx / socket / protocol / timeout retry on backoff; SMTP 5xx, an unparseable recipient, a refused credential and `SsrfBlockedException` dead-letter without retrying; anything **unrecognised is retried but bounded by the retry ceiling**, so a novel failure gives up eventually rather than being dropped immediately. Four bounds are explicit in `EmailOutboxPolicy` (max retry duration, max retention independent of retries, max depth with a **refuse-the-newest** shed policy whose refusal is recorded on the alert row, and the terminal dead-letter/expired states). An unconfigured relay claims nothing — it is not a failed attempt, so no message burns retries against a relay nothing dialed. Security-token mail (password-reset and email-change links) stays on the in-memory, fail-silent `EmailDeliveryQueue`: those bodies are live credentials that an outbox would put at rest in the database, and they are individually re-requestable, which alert mail is not. Invite mail also stays synchronous, because its caller's link-in-response fallback and `CredentialMailPolicy`'s cleartext refusal both need a per-request answer; `email_outbox.message_kind` declares `'invite'` as capacity, with no writer. `coalesce_key` groups burst-dedup — see the breaker/coalescing bullet below — and was recorded from the outbox's first release specifically so that grouping needed no backfill migration onto an existing backlog. `org_id` is nullable so operator-scope mail has a home, which makes the drain, the ceiling sweep and the backlog gauge cross-tenant by design (each carries an `// xtenant:` marker).
- **The relay's health is one fact, not N per-tenant ones — `EmailTransportBreaker` circuit-breaks the shared SMTP transport, and `email_outbox.coalesce_key` collapses alert bursts.** `email_enabled` is untouched by both: the breaker only narrows what `EmailOutboxDeliveryService` claims per pass, and coalescing only changes how many rows a burst produces — neither ever writes tenant configuration, the same posture `RecordEmailFailureAsync` established. Breaker state is process-local and in-memory, deliberately not persisted: a file-backed SQLite deployment already runs exactly one live process (`InstanceLock` refuses a second writer on the same database), so a process-local breaker there is instance-wide by construction; a Postgres deployment can run multiple replicas, each holding its own view of relay health, which is a bounded, self-correcting trade (each replica's claim already goes through `EmailOutboxRepository.ClaimDueAsync`'s per-row lease, so no message is ever attempted twice — the only redundancy is a handful of replicas independently rediscovering an outage and independently probing recovery, never the whole backlog stampeding the relay). Only `EmailOutboxFailureClasses.Transient`/`Unknown` trip the breaker (`RecordTransportFailure`) after `EMAIL_TRANSPORT_BREAKER_FAILURE_THRESHOLD` consecutive occurrences; `Permanent` (`RecordPermanentFailure`) never does — a bad recipient is not a relay outage, and a relay that answers with a definitive protocol verdict has, by that fact, proven itself reachable, which is also why a permanent failure on a probe still closes the breaker. An open breaker admits nothing until `EMAIL_TRANSPORT_BREAKER_INITIAL_COOLDOWN_SECONDS` elapses, then exactly one probe message (never the full batch); a delivered or permanently-failed probe closes the breaker outright, a transport-failed probe reopens it with a doubled cooldown capped at `EMAIL_TRANSPORT_BREAKER_MAX_COOLDOWN_MINUTES` — self-service recovery with no operator action and no stampede on a just-recovered relay. The breaker only ever narrows what gets *claimed*: `EmailOutboxDeliveryService.RunPassAsync` always retires overdue rows via `ExpireOverdueAsync` before it ever consults the breaker, so the four bounds (retry duration, retention, depth, backoff) keep governing every row regardless of the breaker's state. Coalescing is enqueue-time, in `AlertEmailQueue.NotifyAsync`: before inserting a fresh row it looks for an existing `pending` row sharing its `(org_id, coalesce_key)` (matched `IS NOT DISTINCT FROM`, not `=`, so two NULL-org operator-scope rows find each other instead of silently failing to match under SQL's three-valued NULL logic) and, if found, folds the occurrence in — bumping `occurrence_count` and replacing the subject/body with a digest that states the running count and carries the latest occurrence's detail. A coalesced occurrence is never silently dropped: it is recorded as its own `"coalesced"` outcome on its own alert row, distinct from the digest's eventual `sent`/`failed`/`expired` outcome on whichever alert opened it. A race with the delivery worker claiming the target row between the read and the write resolves toward not losing the alert — `TryCoalesceAsync` reports the miss and the caller falls through to a fresh enqueue.
- **The auth stack is an intentional Identity Core hybrid.** Identity Core (`AddIdentityCore`, no SignInManager/cookie scheme) over custom Dapper stores supplies MFA/credential primitives (TOTP, recovery codes, BCrypt, security_stamp). The first-factor login (constant-time + timing sentinel = email-enumeration defense), lockout (`ILockoutStore` keyed on `(realm,tenantId,email)` so unknown accounts are boundable), JWT sessions (HS256 with scope/tid/tver claims that `RouteScopeFilter` and the `ApiToken` scheme depend on), and per-request session invalidation (`tver` claim checked in `OnJwtTokenValidatedAsync` — immediate on password change vs SecurityStampValidator's ~30-min poll) are bespoke for security reasons. `token_version`/`tver` is the canonical session-invalidation signal; `security_stamp` is Identity-internal and rotated alongside it at credential-change sites. Do not migrate the first-factor, lockout, session-issuance, or invalidation layers to `SignInManager`/`Identity.Application`/`SecurityStampValidator` without first revisiting `ADR-auth-identity-hybrid`.

## Git workflow

- **Every code change gets its own git worktree + branch** (`feat|fix|chore/<slug>`) and ships through an MR — never edit the primary `main` checkout directly. `main` is a **protected** branch; a direct push to it is server-rejected.
- **Sync before you branch or tag.** `git fetch origin && git rebase origin/main` (or branch from a freshly pulled `main`). Never branch from, or tag, stale `main` — a branch cut from an out-of-date `main` re-introduces already-merged conflicts and turns green pre-merge into red post-merge.
- **A release tag is created only after the merge lands.** Pull the merged `main` first, then tag — do not tag a branch tip before its MR merges. `validate-release-tag` requires the **annotated** tag to be an ancestor of `main`, point at the current commit, and match `Directory.Build.props` `<Version>`. Release versioning steps live in `CONTRIBUTING.md` → "Versioning".

## Backend/Frontend JSON contract

- **Anything the browser/Svelte frontend consumes serializes camelCase** via `JsonSerializerDefaults.Web` — see `StatsRefreshService.SnapshotJson`, `OrgController`, `OrgSettingsController`. The C# default `JsonSerializer.Serialize(obj)` with no options emits **PascalCase**, which the frontend does not read and which surfaces as a runtime crash, not a compile error. Always pass Web options for frontend-facing payloads.
- **External wire formats deliberately differ.** OSV, SIEM, and audit-event payloads use `JsonNamingPolicy.SnakeCaseLower` (`OsvClient`, `WebhookSiemForwarder`, `PackageEvents`) because their consumers expect snake_case. **Match the consumer, never rely on the C# default.**
- New snapshot/serialization endpoints: verify the emitted casing against the frontend's expectations, and handle `JsonException` on the deserialize side rather than letting it bubble.

## Definition of done

- **A task is done only when the gate is green by exit code, not by tailed output.** Run `dotnet test --filter "Category!=Integration"` and build with `-p:TreatWarningsAsErrors=true` (CI treats warnings as errors when `CI=true`); read the real exit status, not the last scrolled lines of a long log.
- **Before claiming an MR pipeline is green, fetch the actual per-job pass/fail status** — do not infer success from a single "posted note" or a truncated tail. A masked failure read as success is the most common cause of a follow-up fix pass.
- **A green pipeline is not merge clearance — the `ai-review` notes must be triaged first.** The four `ai-review` jobs are `allow_failure: true` by design (a wrong finding must never block a merge), so nothing structurally stops an unread finding from merging; the reviewer is the only gate. Before completing a merge, read the four per-lens MR notes (each marked `<!-- ai-review:<report>.md -->`) and give every finding an explicit verdict — fixed, rebutted with a reason grounded in the code, or filed as a follow-up issue — recorded back on the MR as a single `<!-- ai-review-triage -->` note. This costs almost no wall-clock: `ai-review` runs between `sbom` and `dast`, so its notes land while you are already waiting on the pipeline. Do not arm auto-merge before that triage — arming it at MR-create time makes the review structurally unreadable, because the merge fires on green before the notes exist. A lens reporting `(skipped)`, `(unavailable)`, `(bad response)`, `(low-confidence, suppressed)`, or `(unverifiable response)` — or whose note is missing entirely — is **no signal**, not a pass. `(unverifiable response)` covers a claimed-clean result the model produced without the exact expected phrasing, or one an independent second pass could not confirm — never rendered as a clean pass on an unverified claim alone.
- UI changes ship no emoji codepoints in Svelte (the `dependably/no-emoji` ESLint rule in `web/eslint.config.js` blocks them — via lint-staged pre-commit, `npm run lint`, and the CI `lint` job) — use the `icons.svg` sprite; conventions are in `DESIGN.md` §12.

## Environment variables

The complete reference table lives in [CONTRIBUTING.md → Environment variables](CONTRIBUTING.md#environment-variables) — keep that table as the single source of truth; do not duplicate it here. Behavioral notes that matter when changing code:

- Config keys are written `Section:Key` in `appsettings.json` and code; their environment-variable form uses double underscores (`Rpm__VerifyRepomdSignature` sets `Rpm:VerifyRepomdSignature`). Both spellings refer to the same setting.
- **Storage is two tiers**: *cache* holds proxy artefacts (eviction-friendly); *registry* holds published artefacts (durable, never auto-evicted). `STORAGE_BACKEND`, `LOCAL_STORAGE_PATH`, and the S3/Azure variable pairs all accept `_CACHE` / `_REGISTRY` suffixes for per-tier overrides; unsuffixed values apply to both tiers.
- **`TRUSTED_PROXIES` unset = forwarded headers ignored (fail-closed)**. When unset, `X-Forwarded-For`, `X-Forwarded-Proto`, and `X-Forwarded-Host` are discarded; `Connection.RemoteIpAddress`, `Request.Host`, and `Request.Scheme` reflect the real socket peer. Set to your proxy's IP(s)/CIDR(s) to enable forwarding. A startup warning is logged when unset and a proxy-dependent feature (e.g. HSTS, scheme-relative redirects) may not work as expected.
- **RPM** follows the same per-org `ProxyPassthroughEnabled` gate (default **on**) as every ecosystem — it is not disabled by default; it just ships with no default upstream URL (repos are distro/release-specific). `Rpm:UpstreamMode`: `passthrough` (default) forwards upstream repodata verbatim and refuses hosted publish; `merged` serves local ∪ upstream (local shadows on NEVRA collision) and allows hosted publish. RPM signature trust anchors are per-org and DB-backed (Settings → Trust Anchors); `Rpm:VerifyRepomdSignature=true` is an instance-level override that forces repomd.xml signature verification on regardless of per-org anchor state — with no per-org anchor this fails every resolution closed. The upstream-fetched GPG key is never the trust root.
- **`PROXY_STAGING_PATH`** (proxy-fetch MISS hash-and-stage dir) defaults to the OS temp dir; in containers `/tmp` is often RAM-backed tmpfs, which defeats memory bounding — large-artefact deployments should point it at a disk-backed volume.
- **OCI upstream registries are per-org and DB-backed**, configured in Settings → Proxy → Upstream registries like every other ecosystem (the `upstream_registry` table, `ecosystem='oci'`, with host + repository-prefix routing + auth type). The legacy static `Oci:Upstreams` config array is no longer read. `OciOptions` retains only the instance-level scalars (`Oci:ManifestTagTtl`, `Oci:TokenCacheDuration`, `Oci:UpstreamHttpTimeout`).

## Spec-driven development

Design intent for this repo is committed and indexed in a separate spec
repo: https://gitlab.northwardlabs.ca/moonlitlabs/dependably-community.spec.git

`.sddconfig` at the repo root carries the project half of the setup — the
forge and the spec repo. The half that differs per developer — which RAG

is in `~/.config/sdd/config` and is never committed. Run `sdd doctor` if
retrieval looks wrong before assuming the specs are.

and are **generated, not committed** — so a fresh clone has none of them.
Install the CLI (`npm i -g @dependably/sdd`) and run `sdd init` to render
them, and `sdd update` after upgrading it. This block is the only part of
the setup that is committed, which is why the instruction lives here.

Two rules change how work happens here:

1. **Run a spec review before opening an MR.** Search the spec index for the
   components the change touches and reconcile the change against what the
   specs already claim — in the MR that makes the change, not afterwards.
2. **A change touching a standing spec's `source_refs` either amends that spec
   or records why not.** Code drifting away from a spec that still claims to
   describe it is the exact failure this setup exists to prevent, and it is
   invisible unless the amendment is part of the same change.
